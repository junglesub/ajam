# Notion Connection Webhook Design

## Goal

Notion 카드 속성이 변경되면 aJam 카드 캐시를 자동 갱신하고, 연결된 업무시간·작업일수·가용시간·마지막 작업일을 같은 Notion 카드에 다시 기록한다.

## Architecture

Notion의 무료 Connection Webhook을 사용한다. `page.created`, `page.properties_updated`, `page.deleted`, `page.undeleted` 이벤트를 사용자별 공개 식별자가 포함된 endpoint에서 받고, 최초 verification token을 암호화 저장한 뒤 `X-Notion-Signature` HMAC-SHA256을 검증한다.

실제 처리는 `syncSingleNotionCard(userId, pageId)` 한 경로로 모은다. 이 함수는 Notion 페이지를 조회하고 설정된 data source 소속인지 확인한 뒤 기존 카드 정규화·캐시 upsert·업무 집계·Notion 필드 업데이트 기능을 재사용한다.

## Event Rules

- `page.created`: 페이지가 설정된 data source 소속이면 단일 카드 동기화한다.
- `page.properties_updated`: 제목, 상태, 분류, 시작일, 완료일 중 하나가 바뀐 경우만 동기화한다.
- 업무시간, 작업일수, 가용시간, 마지막 작업일, aJam 업데이트 시간만 바뀐 이벤트는 aJam이 만든 변경으로 보고 무시한다.
- `page.deleted`: 해당 카드 캐시를 stale 처리한다.
- `page.undeleted`: 단일 카드 동기화로 복원한다.
- event ID는 저장해 Notion 재시도를 중복 처리하지 않는다.

## Connection Setup

기존 Notion 연결 modal을 `기본 연결`과 `자동 동기화` 탭으로 나눈다. 자동 동기화 탭에는 사용자별 webhook URL, 구독 이벤트, Notion integration/token 생성과 capability 설정, verification token, 연결 상태, 최근 처리 시각과 오류를 표시한다.

Webhook URL의 공개 연결 ID는 인증 수단이 아니다. 이벤트 실행은 저장한 verification token으로 계산한 HMAC 서명이 일치할 때만 허용한다. token과 서명 원문은 로그에 남기지 않는다.

## Error Handling

verification 요청은 token을 저장하고 200을 반환한다. 서명이 없거나 틀린 이벤트는 401, 알 수 없는 연결은 404, 잘못된 payload는 400을 반환한다. Notion API나 필드 업데이트 실패는 최근 오류에 기록하고 기존 캐시는 보존한다.

## Testing

가장 작은 runnable test에서 HMAC 검증, 입력/출력 속성 필터, verification 처리, 중복 event 무시를 확인한다. 앱 build는 사용자 요청이 없으므로 실행하지 않는다.

## 후속 기능 조사: 상태별 페이지 아이콘 (2026-10-28)

수동 아이콘을 사용하지 않는다는 전제와 기존 아이콘 덮어쓰기, 요청 수 최소화 및 오래 걸리는 일괄 적용의 백그라운드 처리는 사용자 확인을 받았다. **사용자는 중단 시 bulk 메뉴에서 재실행하고 이미 같은 아이콘은 업데이트하지 않는 정책을 선택했다.** 최신 정리는 마지막 두 절을 참고한다. 서버 재시작 후 자동 재개는 제외하며 앞선 영속 작업/lease 설계에 포함한 구현자 가정이었다. 앞의 페이지별 사전 GET, 브라우저 주도 실행과 201회/2~4분 추정은 이전 검토 기록이다. 전체 설계 승인/제품 구현은 아직 진행하지 않았다. 이번 작업은 문서만 변경하고 실제 Notion 데이터, build는 실행하지 않는다.

- **확정:** 수동 아이콘 보호 없이 매핑 이모지 적용, 요청 최소화, 기존 속성과 아이콘을 단일 PATCH로 갱신, 같은 실제 아이콘은 skip, 오래된 bulk snapshot은 Notion 수정 시각과 최신 관측값으로 판별, 브라우저와 독립된 실행, 서버 중단 후 bulk 메뉴에서 수동 재실행, 기존 운영 로그 재사용.
- **현재 최소 구현 제안:** Next.js `after()` + 작업 상태 행 하나. 서버 재시작 자동 재개/페이지별 Item 테이블/상시 작업 루프/외부 큐는 제외한다. 아래의 lease/Item 테이블 설계는 이전 비교안이며 현 구현 범위로 해석하지 않는다.
- **사용자 확정 범위:** bulk는 연결된 Notion data source 전체를 대상으로 한다. aJam 캐시/업무 연결된 카드로 제한하지 않으며 완료/날짜 없는 카드와 aJam 업무 미연결 카드도 포함한다. 휴지통/보관 페이지는 제외하는 기본 동작을 제안한다.
- **용어 구분:** 이번 기능의 bulk는 여러 기존 Notion 페이지에 상태별 아이콘 규칙을 적용하는 일괄 동기화다. 설정 저장 자체는 aJam의 매핑 규칙 저장이며 전체 페이지 쓰기를 자동 실행하지 않는다. 설정을 바꾼 뒤 `전체 아이콘 동기화`를 실행하면 현재 상태와 새 매핑을 기준으로 실제 아이콘이 다른 페이지에만 PATCH한다. 규칙을 바꾸지 않고 다시 Sync하는 경우도 같은 일괄 처리다. 기존 업무시간/작업일수 등의 모든 속성 업데이트를 이번 bulk에 추가한다는 뜻은 아니다. 화면에서는 `Bulk` 대신 `전체 아이콘 동기화`처럼 실제 대상을 설명하는 명칭을 제안한다.
- **별도 질문 없이 제안할 기본 동작:** 미매핑/매핑 해제는 아이콘 유지, 설정 저장과 과거 페이지 적용은 분리, 작업 중 연결/이모지 매핑 변경 시 예전 작업은 중단하고 새 설정으로 수동 재실행, 중복 시작은 진행 중 작업으로 연결한다.
- **Webhook이 연결되지 않은 경우의 기본 동작 제안:** 수동 bulk는 허용하고 자동 상태 반영이 꺼져 있음을 표시한다. 별도 polling 기능을 추가하지 않는다. Webhook 없이 미처 관측하지 못한 외부 상태 변경은 자동 보정이 보장되지 않으므로 최신값 재조회가 필요한 예외 경로를 유지한다.
- `after()` 실행 지속성/브라우저 종료, 같은 페이지의 시간 비교와 쓰기 순서, 재시도/로그 표시 등 기술 검증은 구현자의 책임이며 추가 사용자 선택 항목으로 넘기지 않는다. 100개 시간은 실측이 아닌 추정이다. 제품 구현/build/실제 Notion 쓰기는 아직 시작하지 않았다.

- `Notion 카드` 탭에 버튼과 팝업을 추가해 상태 옵션별 이모지를 설정하고, 상태 변경 시 Notion 페이지 아이콘에 반영한다. 기존 페이지에도 일괄 적용해야 한다.
- `notion-card-workspace.tsx`의 연결/요일 기본 카드 버튼과 기존 modal 패턴을 재사용할 수 있다.
- `retrieveNotionDataSourceSchema`는 스키마를 이미 조회한다. 다만 공개 TypeScript 타입은 property의 id/name/type만 표현하므로 status/select의 options(id/name/color) 타입 확장이 필요하다. 캐시에 등장한 상태만 모으면 미사용 옵션이 누락된다.
- 연결의 `statusProperty`는 이미 `status`와 `select`를 지원한다. 첫 버전은 이 속성을 그대로 쓰고 별도의 상태 속성 선택 설정을 중복 추가하지 않는 방안을 제안한다.
- 기존 Webhook은 서명 확인, event ID 중복 방지, 입력 속성 변경 필터를 거쳐 `syncSingleNotionCard`에서 최신 페이지를 읽는다. 날짜/완료 여부와 무관하게 해당 data source 소속인지 확인한다.
- `syncSingleNotionCard`는 캐시 저장 후 업무 집계 필드도 업데이트한다. 아이콘 전용 일괄 작업에서 이 함수를 그대로 호출하면 불필요한 집계와 쓰기가 발생하므로 최신 페이지 읽기/아이콘 판단 경로만 공유해야 한다. 집계 필드 매핑이 없어도 아이콘은 작동해야 한다.
- 공통 `requestNotionApi`는 REST fetch를 사용하며 현재 429 응답을 로그에 남기고 예외를 던진다. 자동 재시도나 요청 속도 제어는 없다.
- 기존 날짜 후보 query는 100개씩 최대 20회(2,000개)로 제한된다. 전체 기존 페이지 작업에 날짜 필터와 이 제한을 그대로 적용하면 안 된다. `NotionCardCache`도 전체 DB 복제본이 아니다.

### Notion 공식 API 조사

확인일: 2026-10-28. 현재 프로젝트의 API 버전은 `2026-03-11`이다.

- [공식 API 목록](https://developers.notion.com/llms.txt)과 [Update page](https://developers.notion.com/reference/patch-page)를 검토한 범위에서 여러 페이지의 아이콘을 한 요청으로 바꾸는 공개 REST bulk/batch endpoint는 확인되지 않았다. `PATCH /v1/pages/{page_id}`를 페이지마다 호출하는 방식으로 기획한다. 다른 용도의 batch API나 Notion UI의 일괄 편집을 페이지 아이콘 bulk API로 간주하지 않는다.
- 아이콘 요청 예: `{"icon":{"type":"emoji","emoji":"✅"}}`. 본문/상태 값을 바꾸지 않고 아이콘만 갱신할 수 있다. 대상 페이지의 Update content capability와 접근 권한이 필요하다.
- [Data source properties](https://developers.notion.com/reference/property-object)의 `status.options`와 `select.options`에서 상태 옵션 ID/이름/색상을 읽을 수 있다. status는 그룹 정보도 제공한다. 매핑 key는 data source ID + property ID + option ID로 묶어 이름 변경이나 연결 대상 변경 때 다른 상태에 잘못 적용되지 않게 한다.
- [Webhook delivery](https://developers.notion.com/reference/webhooks-events-delivery): 이벤트는 변경 신호이며 최신 값 전체를 담지 않는다. 순서가 바뀔 수 있으므로 처리 시 최신 페이지를 읽는다. 대부분 1분 안에 전달되지만 5분까지 지연될 수 있으므로 즉시 반영을 보장하지 않는다.
- [Request limits](https://developers.notion.com/reference/request-limits): Business/Enterprise는 연결당 600회/분, 나머지는 180회/분이며 워크스페이스 공유 제한도 있다. data source query에는 연결당 약 3회/초의 별도 제한이 있다. 429/529는 `Retry-After`를 따르고, 제한된 횟수의 backoff/jitter를 적용한다. `public_api_request_blocked`는 반복 재시도하지 않는다.
- [Query a data source](https://developers.notion.com/reference/query-a-data-source): cursor로 조회하되 단일 query는 최대 10,000건이다. `has_more=false`여도 `request_status.type=incomplete`이면 전체 완료로 표시하면 안 된다. 이 경우 생성 시각 등으로 범위를 나누어 조회하는 추가 처리나 명시적 부분 완료 처리가 필요하다.

### 최소 기능 제안 — 미확정

1. `상태별 아이콘` 버튼으로 팝업을 연다. 현재 연결/상태 속성과 모든 상태 옵션을 표시하고 각 옵션에 Unicode 이모지 또는 `변경 안 함`을 설정한다. 새 이모지 picker 의존성을 추가하기 전에 기존 입력 방식 재사용을 우선 검토한다.
2. 설정은 기존 사용자별 Notion 연결 저장 방식에 맞는 JSON 필드로 저장하는 방안을 우선 검토한다. 자동 적용 여부도 저장한다. 스키마 재조회 시 삭제된 옵션은 적용하지 않고, 추가된 옵션은 미매핑으로 표시한다.
3. `설정 저장`과 `기존 페이지에 적용`을 구분한다. 저장만으로 과거 페이지 전체를 수정하지 않는다. 미매핑/설정 해제는 아이콘 삭제나 원본 복원을 의미하지 않는다.
4. 자동 적용은 기존 `page.created`, 상태 속성이 포함된 `page.properties_updated`, `page.undeleted` 경로를 재사용한다. 최신 상태의 매핑이 있고 현재 아이콘과 다를 때만 아이콘을 쓴다. 입력 속성이 바뀌지 않은 아이콘/집계 출력 이벤트는 무시하여 순환 갱신을 막는다. 실제 icon 변경 때의 Webhook payload는 구현 검증 대상이다.
5. 일괄 적용은 현재 월/업무 연결/시작일 유무와 무관하게 연결된 data source의 접근 가능한 기존 페이지를 조회한다. 완료 상태도 포함하고 휴지통/보관 페이지는 첫 버전에서 제외하는 방안을 제안한다. aJam 캐시 전체를 조회 대상으로 대체하지 않는다.
6. (이전 비교안; 현재 동작은 마지막 설계안 참고) 적용 전 전체 건수 조회와 페이지별 최신 상태 GET을 검토했다. 요청 최소화 결정에 따라 전체 사전 조회를 반복하지 않고 실행 중 발견 건수를 표시하며 목록/PATCH 응답과 Webhook으로 상태를 확인하는 방향으로 변경했다. 같은 페이지의 Webhook/일괄 쓰기는 직렬화하고 실행 중 설정/연결 변경 시 이전 설정 작업을 중단해야 한다.
7. 진행 중 성공/건너뜀/실패를 구분한다. 한 페이지 실패로 성공분을 되돌리지 않는다. 인증/연결 권한 오류는 작업을 중단하고, 일시적 실패는 제한된 재시도 후 표시한다. 결과 불명확한 쓰기 실패는 최신 상태/아이콘을 다시 읽어 성공 여부를 확인한 다음 재시도한다. 재실행하면 이미 같은 아이콘인 페이지를 건너뛴다.

### 처리 방식 비교 기록 — 사용자는 B 방향 선택

- **A. 기존 서버 액션에서 소량씩 처리(이전 추천, 미선택):** 팝업이 다음 묶음을 요청하고 진행률을 표시한다. 별도 큐/worker/n8n 설정이 필요 없다. 팝업/브라우저를 닫으면 후속 묶음은 멈추고 진행 중 묶음은 끝날 수 있다. 다시 실행하면 처음부터 조회하되 같은 아이콘은 건너뛴다. 브라우저를 닫은 뒤에도 계속 처리한다는 보장은 하지 않는다.
- **B. DB에 작업/진행 상태를 저장하고 서버에서 계속 처리:** 재시작 복구와 브라우저 종료 후 처리가 필요하거나 페이지가 많을 때 적합하다. 작업 claim/lease, 실행 주체와 재개 트리거가 추가되므로 규모와 사용 요구를 확인한 뒤 선택한다. 신규 외부 큐 도입을 전제로 하지 않는다.

### 남은 제품 결정과 구현 검증

- **사용자 확정:** 수동 아이콘은 사용하지 않는다고 가정한다. 매핑된 상태라면 기존 아이콘 유무/종류에 관계없이 매핑 이모지로 덮어쓴다. 자동/일괄 적용에서 같은 정책을 사용하며 별도 덮어쓰기 선택지는 두지 않는다. 미매핑 상태의 기존 아이콘은 유지한다.
- **사용자 확정:** 요청 수를 최대한 줄이고, 오래 걸리는 일괄 작업은 B 방향의 백그라운드 처리를 사용한다. 예상 페이지 수와 보관 페이지 포함 요구는 별도로 명시되지 않았다.
- Unicode 이모지만 첫 범위로 제안한다. 커스텀 이모지/이미지 아이콘 설정, 원래 아이콘 복원 이력, 새로운 상태 속성 생성, 별도 상시 polling은 요청 범위에 추가하지 않았다.
- 구현 시 검증: 미사용 상태 표시, option/property rename과 삭제/추가, 매핑 없음, 동일 아이콘 skip, 덮어쓰기 정책, 신규/완료/날짜 없는 페이지, 중복/역순 이벤트, 출력 이벤트 무시, 일괄 pagination/부분 완료, 429/529/권한 오류, 설정 변경/중단/재실행, 동시 상태 변경을 확인한다.
- 이번 조사는 공식 문서와 저장소 읽기만 수행했다. 실제 Notion 쓰기/권한/이벤트 지연은 실측하지 않았다.

### 덮어쓰기 정책에 따른 데이터/캐시 검토 기록 (2026-10-28)

사용자는 수동 아이콘을 사용하지 않는다고 확인하고 데이터 구조/캐시 전략의 변화 여부를 질문했다. 다음은 그 전제에 맞춘 최소 구조 제안이며 제품 코드는 아직 변경하지 않았다.

- **연결 설정에 JSON 필드 하나 추가:** 예를 들어 `statusIconMappingJson`에 `{ enabled, dataSourceId, statusPropertyId, emojiByOptionId }`를 저장한다. 기존 사용자별 연결 행이 사용자 범위를 제공한다. `emojiByOptionId`는 상태 옵션 ID를 Unicode 이모지로 매핑하고 미매핑 옵션은 키를 생략한다. 대상 data source/property가 달라지면 기존 규칙을 적용하지 않고 재설정하도록 안내한다.
- **원래 아이콘/소유권/덮어쓰기 모드는 저장하지 않음:** 원본 복원을 요구하지 않으므로 페이지별 원래 아이콘 백업과 aJam 관리 여부, `onlyWhenEmpty` 같은 설정은 필요 없다. 설정을 끄거나 매핑을 지워도 이미 적용한 아이콘은 남는다.
- **기존 카드 캐시 테이블 유지:** `NotionCardCache.status`는 현재 화면 표시용 이름으로 유지한다. `normalizePage`는 이미 `rawPropertiesJson.status`에 원본 상태 속성을 저장하므로 옵션 ID를 위한 별도 캐시 컬럼을 바로 추가할 필요는 없다. 실제 아이콘 쓰기는 최신 API 응답의 상태 옵션 ID와 현재 아이콘을 기준으로 판단한다. 오래된 캐시에서 옵션 ID를 읽지 못할 때 이름으로 추측해서 쓰지 않는다.
- **페이지 아이콘의 영속 캐시는 추가하지 않음:** Webhook 처리에서 이미 조회한 최신 페이지의 상태/아이콘과 현재 설정으로 비교한다. 같은 아이콘이면 skip, 다르면 PATCH하고 성공으로 기록한다. 상태 캐시가 같다는 이유만으로 skip하면 이전 PATCH 실패를 복구할 수 없으므로 상태 변경 여부만으로 쓰기 성공을 판단하지 않는다. `lastAppliedEmoji`나 상태별 고정 아이콘 캐시도 필수 데이터로 두지 않는다.
- **스키마는 팝업을 열 때 조회:** 상태 옵션 전체는 기존 스키마 조회 경로로 가져오고 열려 있는 동안만 UI state에 둔다. 새 스키마 캐시 테이블/TTL/주기적 polling을 추가하지 않는다. 이름 변경은 ID 매핑을 유지하며, 새 옵션은 미매핑이고 삭제된 옵션은 적용하지 않는다. 조회 실패 시 저장된 매핑은 보존하고 오류를 표시하며 적용 전 검증을 생략하지 않는다.
- **아이콘 설정 변경은 업무 분석 캐시를 무효화하지 않음:** 이모지 변경만으로 `analysisConfigVersion`을 올리거나 날짜/월 카드 캐시를 전부 재생성하지 않는다. 열려 있는 설정 UI는 새 설정으로 갱신하고, 기존 페이지 변경은 별도 일괄 적용으로 수행한다. 향후 화면에 설정으로 계산한 이모지를 표시하더라도 이를 실제 Notion에 반영된 아이콘이라고 표시하지 않는다.
- **일괄 적용은 캐시를 전체 복제본으로 바꾸지 않음:** 전체 data source 조회 결과는 작업 중 처리하고, 아이콘 변경만을 위해 모든 페이지를 카드 캐시에 넣지 않는다. 기존 부분 캐시 전략은 유지한다. 처리 묶음 시작 시 연결/설정이 실행 시작 때와 같은지 확인하고 달라졌으면 작업을 중단한다. A 방식은 작업 테이블이 필요 없고, B 방식의 작업/진행 데이터는 브라우저 종료 후 계속 처리해야 하는 요구가 확정될 때 추가한다.
- **남는 한계:** 수동 아이콘 보호/복원은 제공하지 않는다. 상태와 아이콘의 외부 변경을 하나의 원자적 작업으로 묶을 수 없으므로 최신 상태 읽기, 페이지별 쓰기 직렬화, 후속 Webhook/일괄 재실행으로 일치를 맞춘다. 아이콘만 외부에서 바꾸는 경우의 상시 감시/즉시 원복은 이번 요구에 포함하지 않는다.

### 100개 처리 시간과 Webhook 요청 결합 검토 기록 (2026-10-28)

- **시간은 실측이 아닌 추정:** 연결된 데이터 소스가 100페이지이고, 전부 매핑되어 있고, 전부 아이콘 변경이 필요하며, 재시도/다른 작업이 없다고 가정한다. 최초 목록 조회 약 1회 + 쓰기 직전 최신 페이지 GET 100회 + 아이콘 PATCH 100회로 약 201회다. 스키마 조회/미리보기 재조회는 소수의 요청이 추가될 수 있다.
- 첫 버전은 요금제와 무관하게 초당 최대 2회 정도로 보수적으로 요청을 분산하는 방안을 제안한다. 전체 약 201회는 이 속도로 약 100초 분량이다. 응답 시간이 요청당 대략 0.3~1초이고 순차 처리/묶음 왕복이 있다고 가정하면 사용자 안내 추정은 **약 2~4분**이다. 이는 SLA나 실제 측정치가 아니다. 429/529 대기, 느린 응답, 다른 Webhook/연결의 요청과 경쟁하면 더 걸린다. 최신 페이지 재조회는 오래된 목록의 상태로 쓰는 위험을 줄이기 위한 것이며 PATCH 직전/직후의 외부 변경까지 원자적으로 막지는 못한다.
- 이미 같은 아이콘인 페이지는 PATCH를 생략한다. 전체 목록이 더 크거나 페이지별 추가 조회가 발생하면 요청 수도 달라진다. 구현 후 기존 API duration 로그로 실제 GET/PATCH 지연과 처리량을 확인하여 추정치를 보정한다.
- **현재 Webhook:** `syncSingleNotionCard`의 페이지 GET 1회 후, 유효한 집계 필드 매핑이 있으면 `syncNotionWorkHoursForPages`에서 속성 PATCH 1회가 나간다. 현재 아이콘 기능은 구현되어 있지 않다.
- **제안하는 Webhook:** 같은 GET 응답에서 상태/현재 아이콘을 읽고, 기존 업무 집계 속성과 변경할 icon을 하나의 `PATCH /v1/pages/{page_id}` 본문 `{ properties, icon }`에 담는다. [Update page](https://developers.notion.com/reference/patch-page)는 두 필드를 같은 요청에 지원한다. 집계 필드를 갱신하는 경우 아이콘 추가로 별도 GET/PATCH를 늘리지 않는다. 아이콘이 이미 같으면 icon만 생략하고 기존 필요한 속성 업데이트는 수행한다.
- 이를 위해 기존 속성 쓰기 helper에 선택적 icon 입력을 추가하고 단일 카드 경로에서 한 번만 쓰도록 조정하는 방안을 제안한다. 집계 필드 설정이 없다는 기존 early return이 아이콘 쓰기를 막지 않게 해야 한다. 속성 쓰기가 없고 아이콘 변경만 필요하면 icon-only PATCH 1회를 보낸다. 속성과 아이콘을 결합한 요청이 실패하면 둘의 성공으로 기록하지 않고 최신 페이지를 확인해 재시도한다.
- **수동 일괄 아이콘 적용:** 업무 집계 필드는 재계산/갱신하지 않고 icon-only PATCH를 사용한다. 자동 Webhook과 쓰기 helper/오류 처리는 공유하되 기존 모든 집계 업데이트 경로에 아이콘 조회를 무조건 추가하지 않는다.
- 위 내용은 설계 제안으로 기록했다. 제품 코드/build/실제 Notion 쓰기 및 성능 측정은 실행하지 않았다.

### 검토안: 요청 최소화 + 재시작 복구를 포함한 백그라운드 일괄 적용

**요구와 범위**

- 사용자 결정: 수동 아이콘 보호 없이 상태별 이모지로 덮어쓴다. Notion 요청 수를 줄이고 오래 걸리는 일괄 적용은 브라우저와 독립적으로 실행한다.
- 상태 property는 기존 연결 설정을 재사용하고 `status`/`select`의 옵션 ID별 Unicode 이모지를 설정한다. 미매핑 상태는 기존 아이콘을 유지한다. 설정 저장과 기존 페이지 일괄 적용은 구분한다.
- 기존 업무 분석/부분 카드 캐시 전략은 유지한다. 원본 아이콘 백업/복원, 외부 큐 도입, 커스텀 이모지 picker, 별도 상시 Notion polling은 첫 범위에서 제외한다.
- 대상은 연결된 data source의 접근 가능한 비보관/비휴지통 페이지 전체이며 완료/날짜 없는 카드도 포함한다. 보관 페이지 제외는 사용자 확정이 아닌 제안이다.

**요청 최소화**

1. 팝업을 열 때 스키마 1회로 상태 옵션을 조회한다. 일괄 적용 전 별도의 전체 미리보기 query를 반복하지 않는다. 실행 전 적용 범위/덮어쓰기 정책을 표시하고 정확한 전체 건수는 조회가 끝나기 전까지 미확정으로 보여준다.
2. 일괄 작업은 data source를 cursor로 조회하며 결과에 포함된 상태 속성/현재 아이콘을 재사용한다. 정상 경로에서 모든 페이지를 GET으로 재조회하지 않는다. 한 묶음 조회 후 처리하고 다음 묶음을 조회하여 전체 목록을 미리 읽어 오래 보관하지 않는다. 업데이트로 순서가 변하는 `last_edited_time` 정렬은 피하고 생성 시각 기준의 고정 정렬을 사용하며 page ID로 중복 작업을 방지한다.
3. 현재 아이콘이 매핑 이모지와 같거나 미매핑이면 PATCH하지 않는다. 이 작업에서는 업무 집계 필드를 업데이트하지 않는다.
4. 성공 PATCH는 갱신된 page object를 반환하므로 그 응답을 확인 데이터로 재사용한다. 응답에 현재 상태 속성이 포함되도록 요청하고, 응답의 상태가 목록에서 본 상태와 달라 매핑이 어긋나면 새 상태에 맞는 후속 쓰기를 제한된 횟수로 수행한다. 상태 변경이 계속되면 반복 쓰기를 무한히 하지 않고 재처리 대상으로 남긴다. 별도의 정상 성공 확인 GET은 보내지 않는다.
5. Webhook은 기존 페이지 GET 1회를 유지하고, 기존 집계 속성 + 변경할 아이콘을 PATCH 1회에 결합한다. 집계 설정이 없으면 icon-only PATCH를 허용한다. icon-only 일괄 요청 때문에 모든 기존 업무 저장 경로에 추가 페이지 GET을 붙이지 않는다.
6. 입력 상태/제목/날짜 등이 바뀌지 않은 aJam 출력 이벤트는 기존 필터에서 API 조회 전에 무시한다. 같은 event ID는 중복 처리하지 않는다. 실제 icon-only/결합 PATCH의 이벤트 payload와 순환 방지 동작은 구현 시 확인한다.
7. 예외 GET은 결과를 알 수 없는 쓰기 실패, 오래 대기했거나 재시작 후 남은 snapshot의 재검증, 응답 상태 누락 등 필요한 경우에만 허용한다. 요청 최소화가 오류 복구와 데이터 범위 검증을 생략한다는 뜻은 아니다.

**예상 요청 수와 시간 — 실측 아님**

- 조회 대상이 100개이고 query가 1회로 끝나며 전부 변경 대상인 정상 경로: 목록 query 1 + PATCH 100 = 약 **101회**. 팝업 스키마 조회, 재시도/상태 경쟁 보정, 일반 Webhook 요청은 별도다. 기존 201회 검토안에서 페이지별 GET 100회를 제거한다.
- 일반적으로 `query 페이지 수 + 실제 아이콘이 다른 페이지 수 + 필요한 예외/경쟁 보정 요청`이다. 같은 아이콘 100개면 작업의 Notion 요청은 query 약 1회로 끝날 수 있다.
- 초당 최대 2회 정도로 분산하면 101회는 약 50초 분량이다. 순차 응답 시간/로컬 처리 등을 포함한 안내 추정은 **약 1~2분**이며 재시도/느린 응답이 있으면 더 길어진다. 공개 API에 전체 작업의 고정 지연 보장은 없으므로 구현 후 운영 로그로 보정한다.
- UI 진행률 조회는 aJam DB만 읽는다. 이 조회가 Notion API를 다시 호출하지 않게 한다. query의 incomplete 응답이나 10,000건 한도는 완료로 숨기지 않고 범위 분할/부분 완료 정책을 적용해야 한다.

**백그라운드 실행과 최소 영속 데이터 — 구현자 제안**

- 현재 Docker는 항상 실행되는 Node 서버이며 `apps/web/src/instrumentation-node.ts`에 서버 시작 경로가 있다. 이 경로에서 앱 내부의 작은 실행 루프를 시작하는 구성을 추천한다. 브라우저나 긴 HTTP 요청에 수명을 의존하지 않는다. n8n을 통한 실행도 가능하지만 별도 주기/연결 설정이 생기므로 이번 기본 방식으로 선택하지 않는다. 서버리스로 이전하면 실행 주체를 다시 정해야 한다.
- 연결 JSON 설정 외에 `NotionIconUpdateJob`과 `NotionIconUpdateJobItem`을 추가하는 방안을 제안한다. Job은 user/source/property, 설정 snapshot 또는 식별값, 상태, cursor/scan 완료 여부, 발견/처리/변경/skip/실패 건수, 실행 시각/최근 오류, 실행 claim/lease 정보를 저장한다. Item은 job/page 고유키, 조회한 상태 옵션 ID와 현재/목표 이모지 등 필요한 snapshot, 처리 상태, 시도 횟수/다음 시각, 오류를 저장한다. 토큰이나 본문 전체는 복제하지 않는다.
- query 결과를 작업 item과 함께 저장한 뒤 cursor를 전진시켜 재시작 시 아직 처리하지 않은 페이지를 잃지 않는다. 같은 source의 중복 실행 버튼은 기존 실행 중 작업으로 연결한다. 연결/매핑이 달라지면 예전 설정 작업은 중단하고 새 설정 적용은 새 작업으로 시작한다.
- claim/lease는 DB에서 원자적으로 얻고 갱신한다. 만료된 claim은 다른 실행 루프가 회수한다. 서버 재시작 후 queued/만료 작업을 재개하고, 서버가 꺼져 있는 동안은 처리하지 못한다. build 단계에서는 작업 루프나 쓰기를 시작하지 않아야 한다.
- 긴 `Retry-After`는 서버 메모리에서 계속 sleep하는 대신 다음 실행 시각으로 저장한다. 페이지별 실패는 격리하고 401/연결 권한 오류는 작업을 멈춘다. 결과가 불명확한 PATCH는 최신 페이지 확인 후 재시도하므로 중복 쓰기를 줄인다. 취소는 아직 시작하지 않은 요청을 멈추며 이미 반영된 아이콘은 되돌리지 않는다.
- 페이지별 Webhook/일괄 쓰기는 같은 직렬화 규칙을 사용한다. 작업 item의 오래된 snapshot보다 더 최신 관측값이 있으면 최신 값을 우선한다. 앱이 보내는 요청은 연결별 속도 제한을 공유하고 일반 Webhook 처리를 일괄 작업보다 우선하도록 한다. Notion 워크스페이스의 다른 앱 요청은 직접 통제하지 못하므로 429/529 대응도 필요하다.
- 작업 item은 전체 카드 캐시가 아니라 실행/복구 기록이다. 완료 작업의 최소 결과는 UI에서 확인할 수 있게 남기고, 불필요한 snapshot/상세 item의 보존 기간은 구현 전에 기존 로그 정리 정책과 맞춰 정한다. 장기 아이콘 관측 캐시나 원본 복원 저장소로 확장하지 않는다.

**상태 경쟁과 검증**

- 목록/PATCH 응답을 재사용하므로 일괄 적용은 동시 편집에 대해 snapshot isolation을 제공하지 않는다. PATCH 응답의 상태로 즉시 보정하고, 그 후의 상태 변경은 Webhook으로 처리한다. Webhook 미설정/누락이나 상태가 지속 변경되는 경우 즉시 최종 일치를 보장하지 않으며 결과에 경고/재처리를 표시한다. API 응답의 상태 필드가 충분한지 구현 검증이 필요하다.
- 검증 대상: 목록/PATCH 응답 재사용, 정상 경로의 개별 GET 없음, 같은 아이콘 skip, 결합 PATCH, 출력 이벤트 무시, 설정/연결 변경 중단, query 저장 중 재시작/중복 버튼/claim 만료, 쓰기 성공 직후 DB 기록 전 중단, pagination/incomplete, 429/529 지연 재개, 취소, 동시 상태 변경/보정 횟수 제한이다. build와 실제 Notion 쓰기는 사용자 요청 없이 실행하지 않는다.
- 이 절은 사용자의 우선순위를 반영한 현재 설계안이다. 실행 루프/테이블 구성과 예외 보정 세부는 제안이며 전체 설계 검토 후 확정한다.
- 별도 구현자 관점 검토 결과, 계획 작성을 막는 중요한 제품 질문은 없었다. 동시 변경의 최종 일치 한계, 예외 GET, 복구 가능한 cursor/item 저장, lease 회수와 연결별 요청 예산을 검토했다. 실제 동작/성능 검증을 대신하는 결과는 아니다.

### Ponytail 재검토: Next.js 실행 의미와 GET 생략의 한계

- **표현 정정:** `Docker 서버 안에서 실행`은 현재 배포된 Next.js의 Node.js 서버 프로세스에서 실행한다는 의미였다. Docker가 작업 큐/스케줄러를 제공하거나 별도 백엔드/컨테이너를 추가한다는 뜻이 아니다. 이 작업은 비동기 네트워크 I/O이므로 별도 CPU worker thread도 전제하지 않는다.
- **요구와 추가 가정 구분:** 사용자는 브라우저와 독립적인 백그라운드 처리를 선택했다. 서버 재시작/배포 후 자동 복구까지 요청하지는 않았다. 앞서 Job+Item 테이블, 상시 실행 루프와 lease까지 기본안으로 확대한 것은 과한 범위 가정이었다. 이전 builder 검토는 그 확장된 범위 안의 실행 가능성을 본 것으로, 최소 범위 선택까지 검증한 것은 아니다.
- **더 작은 후보:** Next.js의 표준 `after()`로 시작 요청 응답 후 처리하고, 작업 상태/건수/오류는 작업 행 하나에 저장한다. 별도 Item 테이블, 상시 실행 루프, 자동 재시작 복구, 우선순위 작업 큐는 기본 요구에서 제외하는 방안을 제안한다. 기존 요청 helper, Webhook, 속성 PATCH와 결합, 부분 카드 캐시는 재사용한다. 중복 시작 방지와 제한된 재시도/오류 표시는 유지한다.
- [Next.js after 문서](https://nextjs.org/docs/app/api-reference/functions/after)는 응답 후 실행 및 Node.js/Docker 배포 지원을 명시한다. 실행 시간은 플랫폼/route의 duration 제한을 받으며 영속 큐나 재시작 복구를 보장하지 않는다. 실제 배포의 장시간 실행/브라우저 종료 동작은 구현 검증 대상이다. 서버 중단 시 작업이 멈출 수 있고 다시 실행하면 목록을 다시 조회해 같은 아이콘을 skip한다. 실행 주체의 종료를 식별해 남은 작업을 `중단됨`으로 표시하는 경로는 필요하다. 사용자는 자동 복구 대신 bulk 메뉴에서 수동 재실행하는 정책을 선택했다.
- **GET 생략의 핵심 한계:** 목록 응답은 조회 시점의 상태다. 예를 들어 목록에서 `진행중`을 읽은 후 사용자가 `완료`로 바꾸면, 예전 목록으로 `진행중` 아이콘을 쓸 수 있다. 같은 페이지의 앱 내부 쓰기를 직렬화해도 Notion의 외부 편집까지 잠글 수 없다. 쓰기 전에 GET을 추가해도 GET과 PATCH 사이의 경쟁은 완전히 없어지지 않는다.
- **보정의 범위:** PATCH가 반환하는 갱신된 page object에 상태/parent가 포함되면 응답에서 관측한 상태 불일치나 대상 변경을 탐지할 수 있다. 다만 공식 문서의 `updated page object`를 동시 편집에 대한 원자적 조건부 쓰기/일관된 snapshot 보장으로 해석하면 안 된다. 처리 전후 상태를 한 트랜잭션으로 묶지 못한다. 오류/상태 누락/오래된 snapshot 등 필요한 경우 GET을 사용하고, 후속 상태 변경은 Webhook과 재실행으로 보정한다. Webhook 미설정/누락 시 자동 보정이 보장되지 않는다.
- **영향 범위:** 아이콘 전용 일괄 PATCH는 상태/본문 값을 쓰지 않으므로 이 경쟁으로 상태나 본문을 덮어쓰지는 않는다. 아이콘이 일시적으로 또는 재처리 전까지 상태와 어긋날 수 있다. 이미 같은 아이콘이라 skip한 페이지도 이후 상태 변경은 별도 Webhook 처리가 필요하다. 조회 후 이동/접근권한 변경 시 오류 처리 및 대상 범위 재검증이 필요할 수 있다.
- **Ponytail 유지 요소:** 새 의존성/외부 큐 없음, 상태 스키마와 연결 설정 재사용, 옵션 ID 매핑, 같은 아이콘 skip, Webhook의 속성+아이콘 단일 PATCH, 정상 경로의 불필요한 GET 제거, 기존 분석 캐시 유지. `모든 Ponytail 요소가 반영됐다`고 단정하지 않으며 실제 구현 diff를 검토한 결과도 아니다.
- **확정한 복구 정책:** 서버 재시작/배포 후 자동 재개는 제공하지 않는다. 중단 표시 후 bulk 메뉴에서 수동 재실행한다. 제품 코드/패키지 설치/build/실제 Notion 쓰기는 아직 진행하지 않았다.

### 수동 재실행과 Webhook/bulk 경합의 구체적 의미

- 사용자는 bulk 메뉴로 돌아와 다시 sync하는 방식을 선택했고, 이미 같은 아이콘은 업데이트하지 않도록 요구했다. 재실행은 이전 메모리의 대기 목록을 이어 쓰는 것이 아니라 Notion 목록을 다시 조회해 현재 상태의 매핑 이모지와 실제 아이콘을 비교한다. 같은 아이콘이면 PATCH하지 않는다. 실패/중단 이력만으로 성공 여부를 추측하지 않는다.
- 사용자가 확인한 경합 예: (1) bulk가 상태 `진행중`, 변경 필요 아이콘을 읽고 `🚧` 쓰기를 준비한다. (2) 사용자가 `완료`로 바꿔 Webhook이 `✅`를 쓴다. (3) 늦게 실행된 bulk가 예전 값으로 `🚧`를 써서 아이콘만 다시 덮어쓸 수 있다. 상태는 `완료`로 남는다.
- Webhook이 이미 처리된 뒤에는 이후 상태 변경 이벤트가 없을 수 있다. 따라서 `Webhook이 언젠가 다시 고쳐준다`만으로 해결된다고 가정하면 안 된다. PATCH 응답의 관측 상태에 따른 제한된 보정, 이미 더 최신으로 관측된 페이지의 오래된 bulk 계획 폐기/갱신이 필요하다. 같은 페이지 쓰기를 단순 직렬화하는 것만으로는 오래된 계획의 늦은 쓰기를 막지 못한다.
- 위 앱 내부 경합 처리와 외부 Notion 편집은 구분한다. 외부 편집까지 원자적으로 잠그지는 못하며 예외 GET/재실행으로 보완한다. 구현할 때 `bulk 목록 조회 → 완료 Webhook 적용 → 오래된 bulk 처리` 순서를 재현하는 집중 회귀 검증을 포함한다.

### 마지막 업데이트 시간 재사용

- 사용자가 지적한 대로, 이미 Webhook으로 더 최신 페이지를 관측한 경우에는 시간 비교로 오래된 bulk 데이터를 가려낼 수 있다. 새 페이지별 버전 테이블을 만들기 전에 기존 `NotionCardCache.lastEditedTime`과 bulk 목록의 `last_edited_time`을 비교하는 방식을 우선한다. 둘 다 Notion이 반환한 수정 시각을 사용하며 앱의 로컬 수신/작업 시작 시각과 섞지 않는다.
- 예: bulk snapshot의 Notion 수정 시각이 14:00이고 Webhook이 관측한 페이지 수정 시각이 14:01이면 bulk snapshot을 폐기한다. Webhook의 성공한 최신 아이콘 쓰기가 확인됐다면 해당 오래된 bulk 쓰기를 건너뛴다. 최신 상태만 캐시에 저장되고 PATCH는 실패한 경우도 있으므로 `더 최신 캐시 = 아이콘 반영 성공`이라고 간주하지 않는다. 이때 최신 상태를 기준으로 다시 판단한다.
- 시각 비교와 실제 PATCH 사이에 다른 aJam 쓰기가 끼지 않도록 같은 페이지의 Webhook/일괄 쓰기를 같은 순서 제어 범위에서 처리해야 한다. 단순히 오래된 snapshot을 차례대로 쓰는 것으로 끝내지 않는다. 캐시 갱신 또한 더 오래된 응답으로 최신 관측값을 되돌리지 않도록 확인한다.
- `last_edited_time`은 페이지 전체의 수정 시각이며 상태 전용 버전/고유 증가 번호가 아니다. 같은 시각이거나 상태/매핑이 다른데 순서를 판정할 수 없으면 동일 데이터로 단정하지 않고 상태 옵션 ID/현재 설정/성공 응답을 확인하고 필요할 때 재조회한다. 아이콘/집계 쓰기 등 다른 수정도 시각에 영향을 줄 수 있으므로 시각만으로 정상 아이콘 여부를 결정하지 않는다.
- 기존 Notion의 `aJam 업데이트 시간` 매핑 속성은 `notion-page-update.ts`에서 PATCH 요청 직전 앱 시각으로 생성하는 값이다. Notion이 발급한 상태 변경 시각이나 쓰기 완료 확인값이 아니므로 위 비교 기준으로 쓰지 않는다.
- 아직 도착하지 않은 Webhook/외부 변경은 로컬 수정 시각 비교만으로 알 수 없다. [Update page](https://developers.notion.com/reference/patch-page) 공개 문서에는 예상 `last_edited_time`이 일치할 때만 쓰는 조건부 PATCH가 명시돼 있지 않다. 따라서 알려진 오래된 작업 제거에는 시간 비교를 사용하고, 남은 외부 경쟁은 PATCH 응답 확인/예외 조회/재실행으로 보완한다. [Page object](https://developers.notion.com/reference/page)는 `last_edited_time`을 페이지가 갱신된 시각으로 정의한다.
- 제품 코드/build/실제 Notion 쓰기는 아직 진행하지 않았다.

### Bulk/아이콘 로그 정책 — 기존 운영 로그 재사용

사용자는 진행/완료/경고/오류/info 기록을 요구했다. 기존 공통 로그와 Notion 로그는 구현돼 있으나 새 아이콘/Bulk 이벤트 정책은 아직 없었으므로 아래를 설계에 추가한다. 이 절은 제품 코드 구현 완료를 뜻하지 않는다.

- `createNotionLog` → `createOperationLog` → 기존 JSON 콘솔 + `OperationLog`/로그 팝업 경로를 재사용한다. 새 logger/로그 테이블/외부 로그 서비스를 추가하지 않는다. 작업 상태 행은 실행 현황이며 운영 로그를 대신하거나 로그로부터 복구하지 않는다.
- 로그 **수준**은 기존 `info`/`warn`/`error`(진단용 debug), 작업 **단계/결과**는 `started`/`progress`/`completed`/`skipped`/`retrying`/`interrupted`/`failed`로 구분한다. `진행`/`완료`를 별도 level로 추가하지 않는다.

| 상황 | 수준 / 결과 | 기록 내용 |
| --- | --- | --- |
| 설정 저장, 작업 생성/실제 시작 | info / completed 또는 started | 사용자/대상 data source, 작업 범위, 시작 시각. HTTP 시작 응답과 실제 Bulk 완료를 구분 |
| 조회/처리 진행 | info / progress | 발견/처리/변경/skip/실패 수, 누적 Notion 요청 수, 경과 시간 |
| 정상 완료, 모두 동일하여 변경 0건 | info / completed | 최종 집계와 총 요청 수. 변경 0건도 정상 완료 |
| 같은 아이콘/미매핑/오래된 계획 폐기 | info / skipped(묶음 집계), 상세는 debug | 고정 reason으로 사유 구분. 정상 skip을 경고/오류로 기록하지 않음 |
| 429/529 등 재시도 가능한 실패 | warn / retrying | HTTP status/errorCode, retryAfter, pageId(필요 시). 복구 가능한 매 시도를 최종 실패 알림으로 만들지 않음 |
| 일부 실패를 포함한 완료/불완전 query | warn / completed | failed/partial과 처리 집계. 일부 실패를 전체 성공으로 표시하지 않음 |
| 서버 종료 등 중단을 나중에 감지 | warn / interrupted | 중단 사유와 마지막 확인된 집계, 메뉴에서 수동 재실행 가능. 강제 종료 순간 로그가 반드시 남는다고 보장하지 않음 |
| 재시도 소진 페이지 실패 | error / page_failed | pageId, 고정 오류 사유/상태/코드. 다른 페이지는 계속 처리할 수 있음 |
| 인증/권한/예상 못한 오류로 작업 전체 중단 | error / failed | 최종 집계와 안전한 오류 코드. 상세를 UI에서 확인 가능 |

- Bulk operation은 `icon_bulk_sync`, 단일 아이콘 동작은 필요한 경우 `icon_update`, source는 `notion_icon_bulk`/기존 `webhook` 등으로 구분하는 방안을 제안한다. 기존 API 요청 로그를 유지하고 아이콘/속성 결합 PATCH를 두 번 성공한 것처럼 중복 기록하지 않는다.
- 실행 작업 ID를 `operationId`로 재사용하고 하위 query/PATCH/재시도/진행 로그에 명시적으로 전달한다. background에도 인증 시 검증한 `userId`를 전달하여 본인의 기존 `내 로그`에 저장한다. 별도 `jobId` metadata를 추가할 필요가 없다. 같은 페이지의 Webhook은 자체 operationId를 유지하며 pageId로 식별한다.
- 저장 metadata는 기존 allowlist를 우선 사용한다: `count`(처리 수), `total`(확인된 경우만), `updated`, `skipped`, `failed`, `requestCount`, `partial`, `reason`, `status`, `errorCode`, `retryAfter`, `pageId`, `dataSourceId`. 조회 완료 전에는 정확한 total/백분율을 꾸며서 기록하지 않는다. 상세 skip reason별 수는 필요하면 별도 요약 이벤트의 reason+count로 남긴다.
- 진행 로그는 최대 5초에 한 번으로 제한하고 시작/최종 결과/오류는 즉시 기록한다. 이미 있는 API 요청별 로그에 매 페이지 info 성공/skip 로그까지 불필요하게 중복하지 않는다. 진행률 UI 조회는 DB만 읽고 Notion 요청이나 로그 조회 자체의 새 운영 로그를 만들지 않는다.
- `createOperationLog.run()`은 2초 이상이면 warn으로 완료 처리하는 공통 규칙이 있다. 정상적으로 1~2분 걸리는 Bulk 전체에 이 wrapper를 그대로 적용하지 않고 `write()`로 시작/완료를 명시하여 예상된 장시간 처리를 경고로 오인하지 않게 한다. 기존 개별 HTTP/API 지연 진단은 유지한다.
- `operation-log-store.ts`의 metadata allowlist 밖 필드는 콘솔에 있어도 DB/UI에서는 버려진다. 구현 시 위 기존 키를 쓰고 필요한 확장은 최소화한다. `log-presentation.ts`에는 새 operation과 progress/retrying/interrupted/page_failed 결과의 한국어 표시를 추가해야 한다. 현재는 해당 새 label이 없으므로 기본 `처리/처리됨`으로 나올 수 있다.
- token/signature, 원문 요청/응답, 카드 제목/본문, 자유 형식 오류 메시지는 DB/UI에 저장하지 않는다. 오류는 안전한 코드/고정 사유로 남기고 기존 보관 정책(info 7일, warn/error 30일)을 유지한다. 큐/DB 장애와 강제 종료 직전 로그 유실 가능성도 기존 정책과 같다.
- 구현 검증에는 진행/완료 구분, 정상 skip/장시간 작업의 불필요한 warn 없음, 부분 실패/재시도/중단 구분, background operationId/userId 전달, allowlist 투영, 한국어 요약, 비밀값 제외, 로그 실패가 본 작업을 막지 않는 동작을 포함한다. 이번에는 문서 변경만 수행하며 build/실제 Notion 쓰기는 실행하지 않았다.
